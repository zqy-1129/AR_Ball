## 一、项目概述

3D 重建需要被摄物体各个角度的照片。这个模块在相机画面上叠加一个「引导球」：
球代表被拍摄的物体，球面上的光点代表需要拍摄的角度。**捕获粒度是「面」而不是「点」**：
镜头正对某个面并稳定停留，该面的全部光点就一起点亮——**一次拍摄 = 一个面（含 21 个点）**，
绕物体转一圈只需 **8 次拍摄**，而不是对着 168 个点逐个拍。

引导球**缩小并停靠在屏幕底部**（独立状态小窗），画面中央完整让给真实的被摄物体。
球体是**灰色底色的半透明球壳**，球面按「**8 个方位扇区 × 整面均匀点阵**」组织：
每个扇区（竖直 45° 楔形）是一片均匀铺开的点阵，镜头正对哪个面，整面的点一起点亮。

引导分四层叠加，任何一层单独看都能用：**球面上的 8 片目标面琥珀高亮**（哪一片没拍）→
**环上的 8 段进度**（拍了几个）→ **中央一句方向指令**（现在往哪转）→
**每点亮一个面的震动**（眼睛不用离开物体）。首次启动另有三页图文引导。

- 平台：**Android**
- 语言 / 构建：Kotlin 2.3 + AGP 9.2.1 + Gradle 9.6，minSdk 26 / targetSdk 37
- 渲染：OpenGL ES 3.0（TextureView + 自建 EGL 上下文）
- 实测：**稳定 60 FPS**，单帧绘制耗时模拟器 0.08 ~ 0.2 ms / 真机 0.2 ~ 1.4 ms；
  **8 个面（168 个点）全覆盖 = 绕物体转一圈拍 8 次**

## 二、系统架构与数据流

三层 View 自下而上叠在一起，各自只做一件事：

```
┌──────────────────────────────────────────────────────────────┐
│ HudView          Canvas 自绘：取景框 / 8 段覆盖环 + 对准进度弧 / │  ← 主线程，随 Stats 重绘
│                  状态芯片 / 快门 / 球体停靠面板 / 方向箭头与     │
│                  方向指令 / 完成横幅 / 首次引导                 │
├──────────────────────────────────────────────────────────────┤
│ GlSphereView     TextureView + 自建 EGL（本层清屏为全透明）    │  ← GL 线程，Choreographer 60fps
│  └ GuideSphereRenderer  ──▶ ScanSession   面级覆盖状态机       │
├──────────────────────────────────────────────────────────────┤
│ PreviewView      CameraX 相机实时画面                          │  ← CameraX 自己的线程
└──────────────────────────────────────────────────────────────┘
        ▲                                    │
        │ 姿态（worldToDevice 3x3）            │ 每 0.2 s 回传 Stats
        │                                    ▼
  OrientationTracker  ─────────────────▶ MainActivity ──▶ HudView.updateState()
  旋转矢量 / 加速度计+磁力 / 手动拖拽        （主线程搬运）
```

一帧的完整链路（全部在 GL 线程内完成，不跨线程同步）：

```
Choreographer.doFrame(frameTimeNanos)
  ├─ dt = (now - lastFrame) / 1e9
  ├─ OrientationTracker.worldToDevice(out9)   // 姿态来源回调
  ├─ ScanSession.update(dt, worldToDevice, autoCapture, shutterPressed)
  │     ├─ 由 worldToDevice 第 3 行解出 camAzDeg → camSector（此刻正对着哪个面）
  │     ├─ 对准 + 停留够久（或按下快门）→ lightSector(s) 把该面 21 点一起点亮
  │     ├─ 增量更新 sectorLitCount → 覆盖度 / 扇区完成态
  │     ├─ camFaceProgress = 当前面对准进度 0..1（HUD 外圈那段细弧）
  │     └─ 推进点亮动画、脉冲、目标面高亮
  ├─ drawShell → drawGrid → drawDots          // 3 次 draw call
  ├─ （可选）drawGradientBackground           // 相机不可用时
  ├─ eglPresentationTimeANDROID + eglSwapBuffers
  └─ 累计 0.2 s → onStats(Stats) 回调 → Handler 投递主线程
```

线程与同步约定：

| 数据 | 生产者 | 消费者 | 同步方式 |
| --- | --- | --- | --- |
| 姿态 `worldToDevice` | 传感器线程 / 主线程（拖拽） | GL 线程 | 回调内写入调用方提供的缓冲；内部用 `synchronized(smoothedQuat)` 保护四元数 |
| 覆盖状态 | GL 线程（`ScanSession`） | GL 线程（渲染） | 同一线程内直接读，无须锁 |
| `Stats` | GL 线程 | 主线程（HUD） | 每 0.2 s 由 GL 线程**拷贝**一份再 `Handler.post`，不共享可变对象 |
| 快门 / 重置 / 模式 | 主线程（HUD 点击） | GL 线程 | `@Volatile` 的一次性标志位，GL 线程消费后自行清零 |

## 四、关键实现

### 1. 为什么是 TextureView 而不是 GLSurfaceView

引导球要**叠在相机画面上**，属于跨 Surface 的 alpha 混合。
`GLSurfaceView` 自带 Surface 且默认不透明，叠在 `PreviewView` 上会直接盖住相机画面。
这里改用 `TextureView` + 自建 EGL 上下文：

- EGL 配置声明 `EGL_ALPHA_SIZE = 8`，`eglSwapBuffers` 前用
  `eglPresentationTimeANDROID` 对齐系统 vsync；
- 清屏为 `(0,0,0,0)` 全透明，只画引导球，相机画面由下层 `PreviewView` 提供；
- 相机不可用时才铺一层渐变底（`drawFallbackBackground`），保证球体始终可见。

### 2. 60 FPS 的做法

- **渲染线程**：`HandlerThread` + `Choreographer` 跟随 vsync，不占用主线程；
  姿态通过 `OrientationSource` 回调从传感器线程取，避免锁竞争。
- **零 GC**：光点状态、矩阵、缓冲全部预分配复用；`ScanSession.update()` 内不产生任何装箱/集合。
- **极少的 draw call**：球壳（索引三角面）、网格线、光点三类几何各自一个静态 VBO，
  每帧只有 3 次绘制；光点用 `GL_POINTS` + 点精灵，一次画完 168 个。
- **着色器无分支、不写深度**，片元开销极低。
- 实测：`drawMs` 稳定在 0.07 ~ 0.2 ms（模拟器）/ 0.2 ~ 1.4 ms（真机 1080×2344），
  预算 16.6 ms，GPU 负载很低，剩余时间全部留给系统。

### 3. 混合模式

| 图层 | 混合 | 理由 |
| --- | --- | --- |
| 球壳 / 网格 | `(ONE, ONE_MINUS_SRC_ALPHA)` 预乘 alpha | 半透明玻璃质感，正确遮挡；球壳改为**灰色底色**（芯部深灰、边缘亮灰的菲涅尔） |
| 引导光点 | `(ONE, ONE)` 加法混合 | 光点像「灯光」一样叠加在相机画面上，暗处也清晰 |

### 4. 姿态来源的三级降级

`OrientationTracker` 按优先级自动选择，任何一级失效都不会出现「转不动」：

1. `TYPE_ROTATION_VECTOR` —— 带陀螺仪融合，最稳，**默认使用这一路**；
2. **加速度计 + 磁力计** —— 设备没有旋转矢量传感器时用 `getRotationMatrix()` 解算；
3. **触摸拖拽 / 自动巡航** —— 完全没有方向传感器时兜底，保证功能可用。

姿态统一为四元数并用 slerp 做**自适应低通**：静止时强滤波抑制抖动，
快速转动时立刻跟上（`1-|dot|` 超过阈值就切到几乎无延迟的平滑系数），避免「球追不上手」的拖影。

#### 「旋转矢量卡死」检测：两路信源交叉验证

有些 ROM / 模拟器上的旋转矢量传感器会**持续上报但姿态恒定不变**，需要一个判据把它识别出来、
切到加速度计+磁力计。这里有个很容易踩的坑（本项目就踩过）：

> 早期版本用的是「旋转矢量 1 秒内姿态没有变化，就认为卡死」——
> 判据是相邻采样间 `1-|dot| > 1e-4`，约等于 1.6°；而传感器上报约 90 Hz，
> **换算下来要求瞬时转速超过 140°/s 才算「在动」**。
>
> 于是这个条件在真机上被无条件触发：用户慢速环绕拍摄时全程都在用噪声更大、
> 易受金属/电子设备磁干扰的加速度计+磁力计解算，只有在猛甩手机时才切回陀螺仪，
> 两路信源还会在阈值附近来回争夺。
> （实测日志：静置时姿态来源稳定显示 `加速度+磁力`，而不是 `陀螺仪姿态`。）

现在的判据不再看「多久没变化」（端稳手机不动本来就是常态），而是看**两个独立信源是否互相矛盾**：

```kotlin
窗口 = 旋转矢量累计转动量 < 0.5° 的连续时间片
卡死 ⟺ 窗口持续 > 2.5s  且  同一窗口内加速度计+磁力计解算姿态变化 > 8°
```

只有当「旋转矢量说自己没转、加速度计+磁力计说设备明明在动」时才判定卡死。
配合「交还主导权前旋转矢量必须累计转够 10°」的迟滞，两路信源不再反复争夺。

手动兜底同样是可自愈的：传感器冷启动时首个采样可能晚到数秒（省电策略），
早期版本用一次性定时器判断「没有传感器」，一旦误判就永久停在手动手势模式；
现在改成周期看门狗，以 `hasSensor`（硬件是否存在且注册成功）为准，
传感器恢复上报后自动交还。

#### 「自动巡航」= 绕物体水平转一圈

「自动巡航」是没有方向传感器时的一键演示入口，它同样要能拍满 8 个面，否则用户会以为功能没做完。

早期实现是在固定俯仰角上做 `14° ± 26°` 的缓慢起伏，**俯仰范围只有 −12°~40°，
相机光轴永远够不到两极**，覆盖率会硬性卡在 72%——正好等于能触及的方向带占比
`(sin62° − sin(−34°)) / 2 ≈ 72%`（实测吻合）。

现在改为**逐带环绕**：按 `80/58/34/6/−22/−48/−76` 七条俯仰带，每条带完整转一圈后
smoothstep 过渡到下一条 —— 与 `.tools/plan.py` 离线验证过的扫描计划一致
（`minU = 0.363`，最脆弱光点仍有约 7.6° 角余量）。
因为每转完一圈方位角正好是 360°，回到 0° 与原来等价，所以换带时方位角天然连续。

**捕获粒度改为「面」之后**，覆盖只取决于水平方位角（镜头正对哪个面就拍下哪个面），
俯仰不再影响覆盖。所以巡航进一步简化成**一条近平视的带**：绕物体水平转一圈（16 s）
就能拍满 8 个面，正好对应 HUD 的提示语「绕物体旋转一周」
（`OrientationTracker.AUTO_BANDS = [8°]`）。七带计划仍保留在 `.tools/plan.py` 里，
作为「逐点」模型的离线分析工具。

### 5. 覆盖判定：由相机朝向直接解出「此刻正对着哪个面」

约定：物体固定在原点，相机始终在它前方 `camDistance` 处，视图矩阵只含平移。
于是「世界」与「设备」的朝向重合，球被施加 `R^T`（世界→设备）旋转后：

```
光点在设备坐标系下的方向 = worldToDevice · n      （n = 光点在世界坐标系下的方向）
```

`worldToDevice` 的第 3 行 `(m6, m7, m8)` 是**相机背向**在世界系的分量，也就是「物体 → 相机」
的方向。它的方位角 `atan2(m7, m6)` 恰好**等于「正对镜头那片光点」的方位角**，
除以 `45°` 就直接得到 `camSector` —— 不需要再与光点方位角相减，也不需要任何视锥计算。

**捕获粒度是「面」而不是「点」**：不再逐点判定「这一片点落没落进取景框」，而是
镜头正对该面并稳定停留（自动采样 `FACE_DWELL_SECONDS ≈ 0.22 s`）、或者按下快门（手动），
就把该面的 21 个点**一次性点亮**（`lightSector()`）。

原因很直接：168 个点逐个去凑，等于要用户对着 168 个方向一次次对准，**拍摄次数太多**；
改成「一次拍摄 = 一个面」之后，**绕物体转一圈只需 8 次拍摄**即可 100%。

> 因此渲染器**不需要相机内参**：`ScanSession.update()` 只接收
> `dt / worldToDevice / autoCapture / shutterPressed`，覆盖判定与 FOV、取景框完全无关。
> HUD 上那个四角取景框现在纯粹是「拍的就是中间这个物体」的视觉引导。

### 6. 光点分布：8 面整面点阵

不再用 Fibonacci 散点，而是把球面按**方位**切成 8 个 45° 扇区（竖直楔形），
每个扇区内部再细分成 `3 个方位列 × 7 个仰角行`，共 `8 × 3 × 7 = 168` 个点：

```kotlin
// SphereGeometry.kt —— 与 App 一致（SECTOR_COUNT_GRID=8, SECTOR_COLS=3, ELEV_ROWS=7, ELEV_SPAN=80°）
az = (s + (c + 0.5f) / SECTOR_COLS) * (360f / SECTOR_COUNT_GRID)
el = -ELEV_SPAN + (row + 0.5f) / ELEV_ROWS * (2f * ELEV_SPAN)
dot = (cos(el)·cos(az), cos(el)·sin(az), sin(el))
```

这样**每个扇区就是一整片均匀铺开的点阵**（= 用户要的「以一整面均匀分布的多个点来标识」），
镜头扫到哪个面，该面的 21 个点**一起点亮**，视觉上是一个被整体标出的面，
而不是零散的单个点。`SPHERE_DOT_COUNT = 8 × 3 × 7 = 168` 与渲染器 `DOT_COUNT` 单一来源同步。

> **点阵只是「一个面」的视觉填充**：21 个点在一次拍摄里被一起点亮，用户不需要逐个去凑。
> 扇区归属在 `ScanSession.init` 用静态 CSR 预计算（见第 11 节），与具体排布解耦。

### 7. HUD

全部用 `Canvas` 自绘，不依赖任何 UI 框架：四角取景框、套在球外的 **8 段覆盖度环**
（半径/圆心由渲染线程实时回传，严丝合缝地跟着停靠到屏幕底部的球）、
FPS/姿态/相机状态芯片、快门、自动采样切换、重置、自动巡航、完成横幅，
以及**球体停靠面板**、**下一角度方向箭头**（见第 10 节）、**首次引导**与**触觉反馈**（见第 12 节）。

工具类小约定：`rect` / `ringRect` / `path` 都是复用的成员对象（逐帧零分配），
但**同一段绘制里一旦把 `rect` 改写成别的矩形，就不能再用它去代表原来的面板** ——
首次引导的「跳过」按钮就踩过这个坑：它读的是刚被改写为按钮矩形的 `rect`，
结果跑到按钮旁边去了。面板自身的边界要单独存局部变量。

### 8. 引导球如何缩小并停靠到屏幕底部

需求是「中间的球应对着中心物体」+「缩小，类似这样在底部」。最直接的做法是改相机位置或
改球的平移矩阵把球推到画面下方，但这两条路都会破坏整套朝向判定：

- 球的**覆盖判定**和**菲涅尔边缘光**都建立在「相机光轴穿过球心」这个前提上
  （球心即物体，物体在正前方）。一旦把球平移出光轴，球面各点的朝向与菲涅尔项全部失真，
  光点会在背面被点亮，等于把核心功能改坏。
- 所以这里**不动相机、不动模型矩阵**，只改**投影矩阵**：把投影中心在纵向上做偏移，

  ```kotlin
  proj[9] = 2f * (SPHERE_ANCHOR_Y - 0.5f)   // SPHERE_ANCHOR_Y = 0.68
  ```

  这是标准的「离轴/非对称视锥」做法：视锥整体下移，球心被投影到画面纵向 68% 的位置，
  但**光线方向、球心朝向、菲涅尔计算全都保持原样**。

球径同步缩小到短边的 34%（`SPHERE_SIZE = 0.34f`），并按
`min(aspect, 1)` 归一，横屏时也不会把球拉扁。实测真机 1080×2344 上
球半径约 **184 px**（`rPx=184`）、球心落在 `cy=1593`（= 2344 × 0.68），
上方 1400 多 px 全部留给真实相机画面里的被摄物体。

配套：`HudView` 的覆盖度环不再写死「画面中心」，而是直接用渲染线程回传的
`sphereCenterXPx/Y` 与 `radiusPx`，所以环、方向箭头、停靠面板三者永远跟球对齐。

### 9. 覆盖的视觉表达：整面点阵（区域光斑通道已删除）

球面光点改成「8 面整面点阵」（第 6 节）之后，**点阵本身已经能清晰表达「哪一片采集过」**：
未采集是深灰点、采集过的整面转青绿。历史版本在光点下面还铺了一层大范围青绿**区域光斑**
（复用光点着色器，用 `uPatch` uniform 切到大尺寸柔光斑通道，靠 over 混合叠成连续色块），
但两层叠加会把「面与面的边界」糊掉，反而看不清整面点阵。**该通道已整体删除**：

- 删除 `GuideSphereRenderer.drawPatches()` 与 `USE_PATCHES`；
- 删除 `PATCH_SIZE_RATIO / PATCH_COLOR / PATCH_ALPHA` 三个常量；
- 光点着色器里的 `uPatch / uPatchColor / uPatchAlpha / uSizeMul` 四个 uniform 与整个片元分支
  一并删除，`DOT_FS` 现在只剩「光点」一条路径，`DOT_VS` 也少了 `uSizeMul` 与尺寸分支。

顺带的两个收益：

1. **跨阶段 uniform 精度隐患彻底消失。** 原先 `uPatch` 同时出现在 `DOT_VS`（顶点段 float
   默认 highp）与 `DOT_FS`（片元段写了 `precision mediump float`）里，必须两处都显式声明
   mediump，否则直接链接失败：
   `Uniform uPatch precision mismatch with other stage. Error: Linking failed.`
   现在两个阶段没有任何共用 uniform。这条坑只在**将来新增共用 uniform**时才需要重新注意
   （规则已写在 `Shaders.kt` 顶部注释里）。
2. **片元少一个 uniform 与一层分支。** 整批片元的 `uPatch` 取值本来就一致、不存在发散，
   但在低端 GPU 上少一个 uniform 读取与分支依然是净收益。

> 点尺寸上限 `GL_ALIASED_POINT_SIZE_RANGE` 仍在启动时查询（真机 1023 px / 部分模拟器仅 64 px），
> 现在只用于诊断上报（写进 `gl_diag.txt`），不再参与尺寸裁剪。

另外，`DOT_FS` 里两处**反向 `smoothstep`**（`edge0 > edge1`，例如 `smoothstep(0.55, 0.0, r)`）
也一并改写成了 `1.0 - smoothstep(小, 大, r)`：部分移动端驱动对反向 smoothstep 的行为未定义。

### 10. 「下一个该拍哪」：整面琥珀高亮 + 环外方向箭头 + 一句方向指令

只告诉用户「哪里没拍」还不够，还得指出**现在往哪转**。三个层次一起给：

1. **整面琥珀高亮（不是单点）**：`ScanSession` 每帧把**目标面的全部未拍点**标成琥珀高亮 ——
   `hintAmount[i]` 向目标值逼近，条件是 `sectorOfDot[i] == targetSector` 且该点未点亮。
   `vHint` 驱动呼吸外环与轻微放大，在整片暗灰点里最扎眼。
2. **环外方向箭头**：目标面中心的世界方向是 `(cos az, sin az, 0)`（世界水平面 = (x, y)、
   竖直轴 = Z），左乘 `worldToDevice` 就得到它在**设备坐标系**下的 `(nextDirX, nextDirY)`，
   也就是它在屏幕平面上的指向。HUD 在覆盖度环**外侧**画一枚琥珀三角箭头指向它，
   接近时淡出（`near = min(1, len / 0.35)`），提示「就差一点了」。
3. **一句方向指令（箭头解决不了的问题）**：箭头只能表达「往这边」，
   而用户往往分不清「该我转身还是该抬手机」。所以中央文字直接把同一个 `(nextDirX, nextDirY)`
   翻译成人话：`HudView.dirWord()` 比较两个分量的绝对值，给出
   **抬高手机 / 压低手机 / 向右转 / 向左转 / 保持不动**（阈值 `t = 0.10`，
   接近光轴时不再催，避免用户手已经在正确位置还乱调）。
   球体停靠面板右下角的状态行复用同一句话，两处永远一致。

三个数据都来自渲染线程每帧回传的同一个 `Stats`（`nextX / nextY / hasTarget`），
不存在不同步的可能。`hasTarget` 为 `false`（8 个面全部采完）时 HUD 不画箭头 ——
早先用的是 `nextZ = -1` 这个哨兵值，现在换成了语义明确的布尔量。

> **修过的一个坑**：早先的实现把目标扇区序号直接乘 45° 当作「设备坐标系下的方向」，
> 漏了 `worldToDevice` 这一步，于是箭头指的是**世界系**方向而不是**相对镜头**的方向，
> 手机转到别的姿态时箭头会指错。现在按上面的方式做了完整变换。

### 11. 物体 360° 环绕采集引导（面捕获 + 分层引导）

**捕获粒度是「面」**：8 个方位面各自绑定球面上的一片点阵（每面 3 列 × 7 行 = 21 点）。
状态机每帧解出「相机此刻正对着哪个面」（`camSector`），镜头正对该面并稳定停留
（自动采样）或按下快门（手动），就把这一面的 21 个点**一次性点亮**——这就是
「**一次拍摄 = 一个面**」的实现，绕物体转一圈只要 8 次拍摄。
逻辑在 `scan/ScanSession.kt`（8 扇区状态机 + 面捕获）+ `ui/HudView.kt`（引导层）。

设计要点：

1. **面 ⇄ 球面点阵绑定（无容差）**：8 个方位面**精确绑定球面上的 21 个点**（每面 3 列 × 7 行）——
   面的「完成」严格等于「这 21 个点全部点亮」。因为捕获本身就是整面点亮，
   所以不存在「面说拍完了、球面还有暗点」的割裂。
   触发条件：`camSector == s`（相机正对该面）并持续 `FACE_DWELL_SECONDS ≈ 0.22 s`，
   或该帧按下了快门——此时整面 21 点一起点亮（`lightSector()`），一个面只产生一次「已捕获」脉冲。
2. **静态 CSR 映射，零运行时开销**：光点方向是**物体本体系**，恒定不变，所以 168 个光点
   → 8 个扇区的归属在 `init` 里一次性用 CSR（压缩行存储）预计算好
   （`sectorStart / sectorDots / sectorDotCount`），并额外存一张反向表 `sectorOfDot`
   （光点 → 扇区，用于整面高亮），运行时只做查表累加，
   不产生任何集合或装箱，符合 `update()` 的零分配约束。
3. **坐标系的关键事实（最高危坑）**：光点方向的**极轴是几何自身的 Y**
   （`SphereGeometry` 生成式 `(r·cosθ, y, r·sinθ)`），但**世界竖直轴是 Z**
   （`QuatMath` 注释 `世界上方向 (0,0,1)`）。求光点的**世界系方位角**必须用
   `atan2(ny, nx)`（世界水平面 x,y），**不能用** `atan2(nz, nx)`（几何极轴 x,z），
   否则 8 个扇区会整体错开 90°。相机方位角用 `worldToDevice` 第三行 `(m6,m7,m8)`
   的 `atan2(m7, m6)`（相机背向在世界系的水平分量）——它恰好**等于「正对镜头那片光点」
   的方位角**，所以直接除以 45° 就得到 `camSector`，不需要再与光点方位角相减。
4. **引导是分层的（中央文字随状态变化）**：屏幕中央（垂直居中 `y=0.46`）不再是一句固定文案，
   而是按状态切换：

   | 状态 | 主文案 | 副文案 |
   | --- | --- | --- |
   | 还没开始（`hasTarget==false` 且未采集） | `缓慢环绕物体` | 镜头对准哪一面，那一面就会亮起 |
   | 正在对准（`camDwell > 0.02`） | `已对准 · 保持不动` | 正在采集这一面 N% |
   | 有明确目标 | `向右转 / 向左转 / 抬高手机 / 压低手机` | 还剩 N 个面待采集 |
   | 全部完成 | `采集完成`（青绿） | 8 个面全部点亮 |

5. **8 段覆盖度环 + 对准进度弧**：环被切成 8 段（每段 45°，段间留 7° 缝），
   **一段就是一个面** —— 环上的信息和球面的 8 片点阵一一对应，用户不用在两种表达之间换算。
   目标段用琥珀呼吸提示「下一段补这里」；环**外**再套一段更细的弧，
   表示「当前这一面已经对准了多少」（`ScanSession.camFaceProgress`）。
   注意这段弧的生命周期很短（`0.22 s` 填满后即整面点亮），它的定位是**捕获前的那一下火花**，
   真正的确认反馈由「整面变青绿 + 震动 + 已捕获 +21」承担。
   左上角面板里的连续进度条也换成了**同构的 8 个小方块**，一眼能看出缺的是哪几面。
6. **方向固定顺时针推进**：`targetSector` 只在「当前目标扇区完成」时 `(t+1)%8` 前进，
   绝不回退为逆时针，避免用户在边界来回时指示方向反复翻转；带 guard 防止死循环。
7. **完成反馈与防抖**：差角走短弧插值；俯仰角 > 87° 时冻结方位角防抖；一个扇区所有光点
   全亮后还要连续稳定 `0.4 s` 才确认完成，防止边界光点闪烁导致扇区完成态抖动。

验证（模拟器）：一键环绕 / 逐面转动，每对准一个新的面覆盖度按 `+21 点`（即 `+1/8`）跳，
8 次后到达 `100% 8/8 个面`（168/168 点），全程 60 FPS，
中央文字依次经过「向右转 → 已对准 · 保持不动 → 采集完成」并弹出完成横幅；
截图见 `deliverables/ux_05_scanning.png`（已拍 3/8 面 + 目标段琥珀呼吸 + 「向右转」）
与 `ux_04_aiming.png`（对准 98% + 环外进度弧）。

### 12. 体验层的两处「慢一拍」设计与首次引导

**a. 重置必须连点两次**。扫到一半误触清空，比多点一下难受得多。第一次点击只是「上膛」：
`resetArmed = true`、按钮变色为琥珀色「确认重置」，`RESET_ARM_MS = 2500 ms` 内没有第二次
点击就自动撤防。撤防逻辑放在 `onDraw` 里按时间戳判断，不需要额外的定时器。

**b. 完成横幅整块可点 = 重新扫描**。扫完之后用户的意图几乎必然是「再来一轮」，
而底部的「重置」为了防误触做成了两步。横幅把最常见的动作放到最显眼、也最不容易误触的位置
（`bannerHitRect` 在 `drawBanner` 里逐帧写入，`onTouchEvent` 按它做命中判定）。

**c. 触觉反馈**（`ui/Haptics.kt`）。举手绕拍时用户多半盯着真实物体而不是屏幕，
所以关键节点给三档震动：按钮轻点、**每点亮一个面**中震、8 个面全满一段庆祝节奏。
实现上 `VibrationEffect.createWaveform`（API 26+ 可用，正好等于 minSdk），
没有马达的设备（部分模拟器）`hasVibrator()` 为 false，全部静默降级为空操作。

> **两个刻意的例外**：① App 冷启动瞬间镜头正对的那个面会在 `0.22 s` 内自动记上
> （「对准即拍」的固有行为），这一次采集**不震** —— 用户什么都还没做，震一下只会让人困惑
> （`HudView.firstCaptureEventSkipped`，一次性豁免）；② 首次引导期间也完全不震。

**d. 首次引导**。第一次看到的是「一个灰球 + 一堆点点 + 一句话」，用户得自己猜该干嘛。
所以首次启动给三页图文：把物体放进取景框 / 绕着物体缓慢转一圈 / 8 个面全亮就完成。
点哪都翻页，右上角「跳过」直达；文案按字符贪心折行（`drawWrappedText`，中文不需要按词断）。

引导期间 **`MainActivity` 把 `renderer.autoCapture` 强制置 false**，看完才恢复。
这样首次启动的进度是从真正的 `0%` 开始，而不是「一打开就已经拍了 1/8」。
完成标记存在 `SharedPreferences` 的 `onboarding_done`，`pm clear` 即可重现引导。
无相机硬件时直接跳过引导并标记完成，否则它永远不会有人来关闭。

## 五、覆盖率与鲁棒性

判断方案好坏不能只看「理论上能不能覆盖」，还要看**最脆弱的光点离取景框边缘还剩多少余量**。

离线复现覆盖算法（`.tools/plan.py`）定义了指标：

```
u = min(sx, sy) / (limY · cz)      u ∈ (0, 1]，越大越稳，u→1 表示正好落在画面正中
```

对不同的俯仰带规划，最脆弱光点的余量 `minU` 如下：

| 环绕带（俯仰角） | 姿态数 | 覆盖率 | minU | 最脆弱光点的角余量 |
| --- | --- | --- | --- | --- |
| 5 带 70/35/-5/-42/-75，4° | 450 | 140/140 | 0.118 | ≈ 2.4° ⚠️ |
| 5 带，3° | 600 | 140/140 | 0.118 | ≈ 2.4° ⚠️ |
| **7 带 80/58/34/6/-22/-48/-76，4°** | **630** | **140/140** | **0.363** | **≈ 7.6°** ✅ |
| 9 带，3° | 1080 | 140/140 | 0.384 | ≈ 7.9° ✅ |
| 9 带，2° | 1620 | 140/140 | 0.408 | ≈ 8.4° ✅ |

**结论**：只扫 5 条俯仰带时，总有 1~2 个光点恰好落在两条带的接缝处，
只有约 2.4° 的角余量——真机上几度的姿态误差（传感器噪声、平滑滞后）就会漏拍，
这就是最初只能做到 96%（134/140）的原因。改成 7 条带后余量提高到 7.6°，
实测一次性达到 **140/140**。

> **注**：本章是**旧版「逐点」模型**（140 点 Fibonacci，`.tools/plan.py`）的离线分析，
> 用来解释「为什么最初只能跑到 96%」。**当前版本已改为「一次拍摄 = 一个面」**：
> 覆盖只取决于水平方位角，绕物体转一圈（8 次拍摄）即 100%，不再存在「点卡在俯仰带接缝」
> 的问题（实测单圈一次性 168/168）。七带计划仍保留在 `.tools/plan.py` 里作为离线分析工具。

另外，增加方位角采样密度（把 4° 改成 3°、2°）或做多遍错位扫描**对 minU 没有帮助**——
因为最脆弱的光点卡在的是**俯仰方向的接缝**，瓶颈不在方位角。
所以「加密俯仰带」才是性价比最高的做法：7 带 4°（630 个姿态）就拿到了理论极限
（约 0.41）的 88%。

> **注**：上表及其结论只适用于**旧「逐点」模型**。当前「一次拍摄 = 一个面」的版本
> 已把覆盖判定与俯仰解耦，**不存在接缝问题**（详见本章开头的说明）。

## 六、可复现的验证方式

模拟器本身没有真实运动，但 Android 的姿态是从**加速度计 + 磁力计**解算出来的，
所以可以反过来：先设计好希望的相机环绕姿态 `(方位角, 俯仰角)`，
再解析地算出对应的加速度计读数（=`世界向上` 在设备系下的表示 × g）
与磁力计读数（=水平指北分量 + 竖直向下分量），通过模拟器控制台注入。

这样 App 走的是**完全真实的传感器代码路径**，而不是被喂了一个假姿态。

```bash
# 绕物体水平转一圈（俯仰固定 8°，3° 步长，5 Hz 注入速率）——一圈即可拍满 8 个面
python .tools/drive.py sweep 1 3 0 1 "8"

# 精确瞄准某个方向（用于补扫 / 定位某个面）
python .tools/drive.py aim "214.1:-69.9;358.3:43.0" 0.3

# 一键：安装 → 启动 → 环绕 → 闭环补扫 → 录屏 → 拉回视频
python .tools/record_demo.py <apk路径> <输出mp4路径>
```

> `record_demo.py` 的演示环绕已简化为**单圈水平环绕**（`ELEVATIONS = (8.0,)`，3° 步长）；
> 补扫目标同步到 App 的 **168 点网格**（不再依赖 `plan.py` 的 140 点 Fibonacci 模型），
> 闭环判定阈值 `168/168`。实测单圈一次性到达 168/168，**零补扫**。
>
> 脚本会先 `pm clear`（好让首次引导重新出现）再 `pm grant` —— **顺序不能反**：
> `pm clear` 会把运行时权限一并撤销，反过来的话整段演示都会被「需要相机权限」遮罩盖住。
> 录屏从引导页第 1 页开始，依次点过三页后自动进入环绕，整段约 36 s。

App 每 0.5 s 会把覆盖率打到 logcat，便于量化验证：

```bash
adb logcat -s GuideSphereStats:I
# I GuideSphereStats: cov=100.0% lit=168/168 faces=8/8 cam=6 target=5 dwell=0% fps=60 drawMs=0.07 rPx=122 cy=1088 next=(0.00,0.00) src=陀螺仪姿态
```

字段含义：

| 字段 | 含义 |
| --- | --- |
| `cov` | 覆盖度百分比（= `lit / total`） |
| `lit` / `total` | 已点亮光点数 / 总光点数（8 面 × 21 点 = 168） |
| `faces` | 已确认完成的面数 / 8（比 `lit` 晚 `0.4 s` 确认） |
| `cam` | 相机当前正对着的扇区（0~7） |
| `target` | 当前建议采集的目标扇区（0~7，顺时针推进） |
| `dwell` | 镜头正对的那个面已对准多久（0~100%），到 100% 整面点亮 |
| `fps` / `drawMs` | 帧率与单帧绘制耗时 |
| `rPx` / `cy` | 球体投影半径与球心纵坐标（用来核对「球停靠到底部」，`cy ≈ 屏高 × 0.68`） |
| `next` | 目标面在设备系下的水平方向，HUD 据此画箭头与方向指令 |
| `src` | 当前姿态来源：`陀螺仪姿态` / `加速度+磁力` / `自动巡航` / `手动接管` / `触摸旋转` |

实测每个新面被镜头正对时，`lit` 精确按 **+21** 跳（= 一个面的 21 个点），
8 次后到 `168/168`：
`21 → 42 → 63 → 84 → 105 → 126 → 147 → 168`。

### 用像素度量验证「瞬态」视觉

对准进度弧只存在 `0.22 s`（填满即整面点亮），截图基本抓不到它 ——
但这不代表它没画出来。与其反复盲拍，不如**量化**：这段弧画在球心外
`r ≈ ringRadius + 7dp` 处，而 8 段环位于 `r ≈ ringRadius`，所以
`r ∈ [151, 160] px` 这条环带里除了对准弧不该有别的青色元素。
对一批连拍统计该环带的青色度 `(G+B)/2 − R`：

```
      d8.png  mean= -25.96  max= 147.50   ← 弧在
      f2.png  mean= -20.17  max= 148.50   ← 弧在
      f5.png  mean= -29.33  max= -16.00   ← 弧不在
```

30 张连拍里恰好 5 张出现 `max ≈ 148` 的跃升（≈ 22.5°/s 巡航下的占空比），
说明这段弧确实在按预期渲染。**凡是有「转瞬即逝」的视觉改动，都用这种度量代替肉眼看运气。**

`fps` / `drawMs` 用来核对渲染预算（16.6 ms / 帧）；`src` 是传感器仲裁的观测点 ——
如果它一直在 `陀螺仪姿态` 和 `加速度+磁力` 之间来回跳，说明旋转矢量卡死判据的阈值需要复核
（见第 4 节）。

#### gl_diag.txt：绕开 ROM 的 logcat 限流

一加 / OPPO 的 ROM 对每个应用在 logcat 里的行数有配额（`LOG_FLOWCTRL`），
超出后**应用自身的日志会被静默丢弃**。引导球早期的 GLSL 链接失败就是这样被藏住的：
渲染线程起不来、画面全黑、崩溃栈也没有，logcat 里却什么都看不到。

现在渲染线程会把关键节点**落盘**到 `getExternalFilesDir()/gl_diag.txt`：

```
EGL 就绪 config=... 
GL 资源创建完成 点尺寸上限=1023.0
首帧渲染完成 1080x2344
```

```bash
adb shell run-as com.remy.guidesphere cat /sdcard/Android/data/com.remy.guidesphere/files/gl_diag.txt
```

排查时只要看这个文件有没有停在某个阶段，就能立刻定位是 EGL、编译还是首帧的问题。
（顺带记一个 GL 坑：GLSL ES 3.0 里**同一个 uniform 若在顶点段与片元段都出现，两处必须声明一致的精度**
——顶点段 float 默认 `highp`、片元段默认 `mediump`，不写精度限定符会直接链接失败。
当前版本两个阶段已经没有共用 uniform，但新增时仍要遵守这条规则。）

## 七、已知限制

- **`inFrameUnlit` 提示**：底部停靠面板里的「框内 N 个」指的是**当前正对的那个面**里
  还有多少点没记（例如刚进入一个新面时是 `21`）；整面记下后立刻变 0，
  所以自动采样模式下它大部分时间是 0，主要在刚换到新面时闪一下。
- **「对准即拍」意味着开场就有一面算已拍**：自动采样模式下，镜头正对的那个面
  停留 `≈0.22 s` 就会被记为已拍，所以 App 一启动、镜头对着物体时，覆盖度就是
  `1/8（12.5%）` 而不是 0——这是「一次拍摄 = 一个面」的固有行为，不是 bug。
  若只想手动记录，切到「手动快门」模式即可（只有按快门才整面点亮）。
- **模拟器性能不代表真机**：本项目的 60 FPS 是在开启宿主机 GPU 加速
  （`emulator -gpu host`）下测得的；软件渲染（swiftshader）只能跑到约 22 FPS。
  真机上这套渲染负载很轻（0.1 ms / 帧），不存在瓶颈。
- **捕获判定不含任何透视投影**：判定只问「相机此刻正对着哪个方位面」，不涉及 FOV、
  不涉及球面点在屏幕上的实际投影位置。收益有两个：一是**判定与「球怎么转、镜头什么焦距」
  彻底解耦**，斜着拍（俯仰角很大）也不会因为投影变形而漏判；二是计算量极低（只有一次
  `atan2`）。代价是**俯仰方向的覆盖不进判定**——上下两极依靠球面点阵「是否点亮」来呈现，
  但一次拍摄并不要求把上下都拍全。若将来需要「上/下也各算一个面」，把扇区改成
  8 方位 × 3 俯仰 = 24 个面即可，`ScanSession` 的 CSR 与状态机结构不用动。
- **演示视频是模拟器录制**：`guidesphere_demo.mp4` 在模拟器上用 `adb shell screenrecord` 录制，
  相机画面是模拟器内置的合成场景（真机一加 PKX110 的 ColorOS 封禁了 `screenrecord` 写文件，
  详见第八节）。视频里的姿态来自模拟器控制台**注入的真实加速度计/磁力计读数**，
  走的是 App 真实的传感器代码路径，不是播放动画。
  真机则用 `guidesphere_real_device.png` 截图 + 遥测数据验证**性能、相机与观感**，两者互补。
- **自动巡航 + 手动快门 = 覆盖率不动**：覆盖累积只发生在「自动采样」模式下
  （镜头正对一个面并稳定停留 `≈0.22 s` 才整面计分）；「手动快门」下必须按快门才整面点亮。
  所以如果开着自动巡航、模式却停在「手动快门」，球在转、覆盖率却一直是 0，很容易被误判成功能坏了。
  录制演示视频时确实踩到过这一条（第一次录出来全程 0%）。默认启动是「自动采样」，正常路径不会遇到。
- **未覆盖提示是「整面琥珀高亮」**：目标面的 21 个点整片染成琥珀并做呼吸脉冲，
  其余未覆盖面保持暗灰。这样「琥珀 = 下一个要拍的面 / 暗灰 = 还没拍 / 青绿 = 拍过了」三态分明；
  不再把**所有**未覆盖区都染琥珀，避免和青绿已覆盖区争夺视觉焦点、看不出优先级。

### 真机录屏的一个坑：ColorOS 把 `screenrecord` 封了

这台一加（ColorOS / Android 16）**完全不允许 `adb shell screenrecord` 写文件**：

```bash
$ adb shell screenrecord /data/local/tmp/x.mp4
Unable to open '/data/local/tmp/x.mp4': Permission denied
```

排查结论（都不是「路径写错」这么简单）：

| 假设 | 实测 |
| --- | --- |
| 磁盘/权限问题 | 同为 shell 用户，`touch /data/local/tmp/x` 正常 ✓ |
| 目录不对 | `/sdcard`、`/sdcard/DCIM`、`/sdcard/Download`、`/sdcard/Android/data/<pkg>/files`、`/data/local/tmp` **全部**被拒 |
| 文件已存在导致 | 预先建好同名文件并 `chmod 666`，照样被拒 |
| 用流式输出绕开 | 该 ROM 的 `screenrecord` 是裁剪版，帮助里没有 `--output-format`，`exec-out screenrecord -` 不可用 |

所以是 **SELinux 针对 screenrecord 进程的写策略**，不是 DAC，也不是参数问题。
（顺带排除：`com.oplus.screenrecorder` 存在但没有 launcher 入口，导出的 `am start` 动作一律 SecurityException，
没法从 adb 驱动厂商录屏。）

最终采用的办法：**演示视频在模拟器上录**（相机画面是模拟器内置的合成场景），
真机表现则用 `guidesphere_real_device.png` 这张实拍截图 + 遥测数据佐证。
`screenrecord` 在模拟器上工作正常。
